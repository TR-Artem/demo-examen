## Схема (8 таблиц)

```
roles 1—M users
categories 1—M products
products 1—M product_items M—1 sizes
users 1—M orders
orders 1—M order_items M—1 product_items
```

Почему так:

* **размеры** — отдельная таблица (35 значений), а не столбцы;
* **товарная позиция** = модель + размер, у неё свой остаток;
* **order_items** хранит количество и цену за единицу на момент заказа;
* итог заказа **не хранится**, а считается:
  `SUM(order_items.quantity * order_items.unit_price)`;
* `UNIQUE(product_id, size_id)` — одна позиция на пару «модель+размер»;
* `ON DELETE CASCADE` у строк заказа, `RESTRICT` у позиции, которая уже заказана.

## Что упрощено (доделай для «5»)

1. **Изображения**: в каталоге показывается имя файла/заглушка, в карточке —
   рамка с подписью. Для реальных фото добавь `Pillow` и `ImageTk.PhotoImage`,
   ресайз под макет, папку `img/`.
2. **Блок-схема и ER** не генерируются кодом — нарисуй по шаблонам из
   `materials/` и сохрани в PDF.
3. **Руководство пользователя** — заполни шаблон своими скриншотами
   (каталог, корзина/заказ, заказы, статистика).
4. **Валидация даты** — базовая (`ГГГГ-ММ-ДД`); на экзамене добавь проверку
   «дата не в будущем», если этого требует куратор.
5. **Один товар = одна позиция в корзине**: при повторном добавлении создаётся
   вторая строка. Для «5» объединяй по `item_id`.
6. **Менеджер vs Администратор**: менеджер создаёт/удаляет заказы, админ ещё
   меняет дату и удаляет позиции — проверь по своему КИМ.

## Как перенести на свою предметную область

Структура почти всегда одна:

```
справочники (роли, категории, размеры/ед. изм., статусы)
        ↓
основная таблица (товары/услуги) — только *_id ссылок
        ↓
позиции (товар + размер/характеристика + остаток)
        ↓
документы (заказы) + строки (позиция, количество, цена)
        ↓
пользователи + роли
```

Меняются названия полей и правила (скидка, подсветка, статусы) — каркас тот же.
